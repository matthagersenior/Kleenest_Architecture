# Autonomous Architecture Batch Plan

The work is intentionally grouped so large numbers of similar tasks can be completed without repeatedly stopping for approval.

## Batch A — Identity / access

- audit auth service and AuthContext
- map profiles/subscriptions/entitlements/pricing
- define canonical identity provider
- define entitlement gate
- record every current consumer

## Batch B — Locations / maps / routing

- audit location/map/routing consumers
- identify canonical location query/read surfaces
- identify map discovery and ingestion boundaries
- define location normalization
- define route plan/stops/events contract
- define offline boundary

## Batch C — Consumer location actions

- check-ins
- reviews/photos/likes
- favorites
- QR scan/attribution/redemption
- verification and contributor observations
- customer review amenity inventory, including count of each amenity observed at the location
- occupancy measurement model that can represent current occupancy, capacity, utilization, queue/wait signals, confidence, freshness, provenance, and privacy-safe aggregation

## Batch D — Social / communication

- follows
- posts
- likes/comments/saves/reports
- activity
- messages
- family

## Batch E — Progression

- points
- badges
- levels
- streaks
- actions/games/challenges
- contests
- reputation/milestones
- comprehensive badge catalog across verified visits, evidence quality, amenity verification, occupancy contributions, reviews, routes, streaks, community helpfulness, quests, games, QR activity, and contributor trust
- comprehensive reward rules with authoritative point transactions, deduplication/idempotency, milestone rewards, badge rewards, challenge rewards, contest rewards, and visible reward history

## Batch F — Commercial surfaces

- businesses
- campaigns/events/promotions
- memberships/clubs
- certifications

- partner programs

## Batch G — Enterprise / Fleet

- enterprise networks/campaigns/outcomes
- fleet vehicles/drivers/routes
- alerts/maintenance/scorecards/metrics
- fleet-owner operational notifications generated by geofence entry/exit/dwell events
- fleet-owner operational notifications generated by job/route/stop completion and failure states
- notification routing to authorized fleet owners/managers/operators in addition to any consumer-facing messaging
- occupancy-aware route and stop intelligence where trustworthy occupancy signals exist

## Batch H — Platform intelligence

- intelligence jobs
- action links
- notifications
- push subscriptions/delivery
- live network
- analytics/data features
- admin/support
- occupancy trend/quality analytics with confidence/freshness and no false precision
- notification event provenance so owner alerts identify the triggering geofence/job/route/stop event

## Current large implementation wave — Trust + Fleet Operations + Progression

1. **Review amenity inventory** — extend verified customer reviews/evidence to record amenity type and observed quantity; aggregate counts into canonical location detail data.
2. **Occupancy measurements** — add a provenance-aware occupancy observation substrate with count/capacity/utilization/queue fields, confidence and freshness; expose only privacy-safe aggregate signals.
3. **Fleet event-driven notifications** — generate owner/operator inbox + push notifications from authoritative geofence and job/route/stop completion/failure events instead of relying only on owner-authored outbound notifications.
4. **Comprehensive badges/rewards** — expand the badge/rule catalog, connect authoritative events to progression, preserve idempotency, and make earned outcomes visible across contribution and progression surfaces.
5. **Cross-cutting acceptance** — authorization, RLS/grants, telemetry, realtime/offline behavior, refresh, migration parity, audits, and production build must converge for the whole wave.

## Batch execution rule

For each batch:

1. inspect Production authority;
2. inspect all known `Kleenest_App` consumers;
3. identify duplicate consumers;
4. classify parity;
5. write the Architecture contract;
6. only then implement code;
7. run validation/build checks where available;
8. commit as one coherent batch.

No speculative rewrites. No copying historical folders wholesale. No deleting the reference implementation while the Architecture contract is still being derived.
